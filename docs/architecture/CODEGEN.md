# Tula Code Generator — Lowering to Bytecode

The **code generator** is the first half of the engine's backend. It takes the AST
produced by the parser and **lowers** it into **bytecode** — a compact, linear
sequence of simple instructions that the virtual machine can execute.

```
 AST (tree)  ──►  code generator  ──►  bytecode  ──►  .tbin  or  VM
```

"Lowering" is the key word: the AST is a high-level, human-shaped tree, and
bytecode is a low-level, machine-shaped list. The code generator is the bridge
between those two worlds.

## Why turn the tree into something flatter

The AST is ideal for *understanding* a program — its shape mirrors the source and
makes structure explicit. But it is a poor thing to *execute* directly: walking a
branching tree over and over, re-deciding at each node what to do, is slow and
awkward. Bytecode trades the tree's structure for three properties that matter at
run time:

- **Linear and simple.** Execution becomes a straight walk through a list of tiny,
  uniform instructions — far faster and simpler than re-traversing a tree.
- **Compact.** The program shrinks to a dense sequence of operations plus a pool of
  its constant values.
- **Serializable.** A flat sequence can be written to a file and reloaded later,
  which is exactly what makes ahead-of-time compilation possible.

## What lowering actually does

The code generator walks the AST and, for each construct, emits the instructions
that carry out its meaning:

- An **expression** becomes instructions that compute its value — operands first,
  then the operation that combines them.
- A **variable or constant** definition or assignment becomes instructions that
  produce the value and then store it; a reference becomes an instruction that
  loads it.
- **Control flow** (`if`, `while`, `do`, `for`, `break`, `continue`) becomes
  conditional and unconditional **jumps** between positions in the instruction
  sequence — the nested tree is flattened into a line, with jumps that skip or
  repeat regions of it.
- **Functions** become addressable blocks of instructions; a call becomes an
  instruction that transfers control to one, and `return` an instruction that
  transfers back.
- **Literal values** are gathered into a pool of constants that instructions refer
  to, rather than being embedded inline.

Crucially, the code generator decides *how each language construct is expressed as
instructions*, but it does not decide *what those instructions ultimately mean* —
that is the virtual machine's role. The two must agree on a shared instruction
vocabulary, and that agreement is the bytecode format.

## Positions come along for the ride

Lowering preserves the **source positions** attached to AST nodes, threading them
into the generated bytecode. This is what allows a problem discovered much later,
while the program is running, to still be reported against the original source
line and column — even when the program is executed from a precompiled file with
no source in sight.

## Where it sits

The code generator is the point where Tula stops *analyzing* a program and starts
*preparing it to run*. Its input is the AST and nothing else; its output is
bytecode and nothing else. That output can travel two ways — written to a `.tbin`
file for later, or handed straight to the virtual machine in memory — but the
generation work is identical either way. Producing bytecode in exactly one place,
regardless of destination, is what guarantees a program behaves the same whether it
was compiled ahead of time or run directly from source.
